## Recovery decision frozen by S5

The operation phase and `rootfs_state` are separate durable facts:

- before engine invocation, cold recovery records `failed/absent`; an explicit
  retry generates a new non-reusable alias;
- after successful install but before start invocation, cold recovery records
  `failed/installed`; an explicit retry reuses that proven rootfs and alias;
- once install or start may have produced an unobserved external effect, loss
  of the live child handle records `unknown`; status and failed `down` cause no
  automatic engine action, and the artifact is preserved.

Manual cleanup in the harness was a separate test-owned action. It required
the exact persisted engine session ID plus qualified containment and public
observations, then removed only the exact disposable alias. This procedure is
not an automatic production fallback.
